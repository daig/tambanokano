# A3 — Order-sorted type system (deep-dive report)

**1. Functional scope.** Sorts (well-defined data) vs kinds (error supersorts = connected components), the subsort partial order, and the "give-it-the-benefit-of-the-doubt" partiality model (manual 517–533, 973–1063, 1127–1159). Operator declarations with domain/range sorts, subsort + ad-hoc overloading, and the requirement that overloaded decls agreeing on domain kinds must agree on range kind (973–1125, 1161–1174, 11154–11178). Preregularity = every term/equivalence-class has a least sort; the engine computes that least sort and warns on failure, including preregularity *modulo* assoc/comm/id/idem (1197–1223, 2208–2234, 11180–11220). Memberships / sort constraints `mb`/`cmb` that lower a term's sort (1429–1545). Constructors via `ctor` and ctor-consistency (the SCC sufficient-completeness tool is separate) (1642–1724). Polymorphic ops (`poly`) instantiated at kind level (1726–1744).

**2. Architecture in C++.** A `Sort` (`sort.hh:35`) is a `NamedEntity` holding `subsorts`/`supersorts` vectors, a `sortIndex`, a `fastTest` int, and `leqSorts` (a `NatSet` bitset of indices ≤ it). A `ConnectedComponent` (`connectedComponent.hh:31`) = a kind; its ctor (`connectedComponent.cc:43`) synthesizes the error sort (index 0 = `KIND`/`ERROR_SORT`, `sort.hh:40`), then linearizes the poset top-down so maximal sorts get low indices and the error sort is the supremum — via a union-typed counter `sortIndex`/`nrUnresolvedSupersorts` (`sort.hh:81`) decremented in `processSubsorts` (`sort.cc:89`); cycles → module marked bad. `computeLeqSorts` (`sort.cc:102`) fills each `leqSorts` and `fastTest` (smallest index whose tail is all-≤-us). `leq` is bitset containment (`sort.hh:146`); `findIndex`/`findMaximalSorts` compute GLBs and maximal covers (`connectedComponent.cc:88,104`).

Sort computation is *compiled*, not interpreted. `SortTable` (`sortTable.hh:34`, an abstract base of `Symbol`) stores `opDeclarations` and a flat `sortDiagram` (`sortTable.hh:129`): a deterministic decision DAG where `traverse(pos, sortIndex)=sortDiagram[pos+sortIndex]` (`sortTable.hh:209`) is walked once per argument to reach a final range-sort index. `buildSortDiagram` (`sortTable.cc:251`) builds it argument-by-argument: for each candidate arg sort it intersects the viable declaration set, `minimize`s by domain subsumption (`sortTable.cc:225`), and at terminals calls `findMinSortIndex` (`sortTable.cc:369`) — the least-sort via NatSet intersection of range `leqSorts`, whose `unique` flag *is* the preregularity check (breaking ties toward the earlier declaration). Failures collect into `badTerminals` → `sortErrorAnalysis` (`sortErrorAnalysis.cc:37`) which counts bad sort-tuples for the warning. A parallel `ctorDiagram` (`ctorDiagram.cc:166`) computes ctor status (`IS_CTOR|IS_NON_CTOR|IS_COMPLEX`, `sortTable.hh:39`). `Symbol::fastComputeTrueSort` (`symbol2.hh:29`) shortcuts via `uniqueSortIndex`. For assoc/comm ops, `BinarySymbol::computeSortIndex=traverse(traverse(0,i1),i2)` and `computeMultSortIndex` square-and-multiply over multiplicity (`binarySymbol.hh:171`); `commutativeSortCompletion` adds swapped decls.

`SortBdds` (`sortBdds.hh:34`) encodes sorts as bit-vectors for order-sorted unification: per-component `gtRelation` and per-sort `leqRelation` BDDs (`sortBdds.cc:41`), per-symbol sort functions built on demand from the sort diagram (`getSortFunction`, `sortBdds.cc:117`; recursive + linear cross-check in `computeSortFunctionBdds`, `sortTable.cc:392`), and `operatorCompose` (`sortBdds.cc:292`). Built on the external BuDDy library (`bdd.hh`/`BddUser`).

Memberships: `SortConstraint` is a `PreEquation` + target `Sort` (`sortConstraint.hh:30`). Per-symbol `SortConstraintTable` (`sortConstraintTable.hh:29`) orders constraints smallest-sort-first (`sortConstraintLt`, `sortConstraintTable.cc:58`) and `constrainToSmallerSort2` (`sortConstraintTable.cc:119`) repeatedly matches/checks/lowers a dag node's sort, retrying from the top after each success. Dispatch pattern: deep **multiple inheritance** — `Symbol` IS-A `SortTable`, `SortConstraintTable`, `RuleTable`, … (`symbol.hh:42`); per-theory sort behaviour via virtuals (`computeBaseSort`, `symbol.hh:88`).

**3. Rust migration.**
- **Sort/Kind poset — PORT (data) / RETHINK (build).** `SortId(u32)` indices into module `Vec`s; no `Sort*`. `Kind` holds sorts in topological order; per-sort `leqSorts` as `fixedbitset` (counts are small/dense), `leq` = bitset test. Replace the union counter + recursive `registerConnectedSorts` with an explicit Kahn topological sort (hand-rolled or `petgraph`) that returns `Result` on cycles. Rationale: separate transient build state from immutable `SortData`; integer encoding (error=0, supersorts low) preserved because BDD bits, `fastTest`, and the diagram depend on it.
- **Sort/ctor diagrams — PORT.** Flat `Vec<u32>` with arithmetic `traverse`; the build algorithm and `findMinSortIndex` port almost verbatim. This data-oriented DFA is already idiomatic Rust.
- **`Symbol` multiple inheritance — RETHINK.** Composition: `struct SymbolCore { sort_table, mb_table, … }`; theory-specific `computeBaseSort`/`makeDagNode` via the same enum-dispatch-vs-trait-object choice A1/A2 make. Sort computation stays *data* in `SortTable`, not a vtable.
- **`NatSet` — ADAPT** → `fixedbitset` (or `roaring` for sparse big components). Drop the `fastGeq`/small-int hack.
- **`SortBdds` — RETHINK, feature-gated.** BuDDy is C. Use a pure-Rust BDD (`biodivine-lib-bdd` or `oxidd`) behind a `unification` feature; needed only for symbolic reasoning (A8), so defer. Keep one BDD construction path (drop the debug recursive/linear cross-check).
- **Memberships — PORT/ADAPT.** `SortConstraint` shares the statement/`PreEquation` representation with A2/A6; `constrainToSmallerSort` becomes a method driven by the A1 reduce loop.
- **Does NOT translate:** the `sortIndex`/`nrUnresolvedSupersorts` union; the multiple-inheritance hierarchy; raw `Sort*`/`ConnectedComponent*` graphs; BuDDy FFI; `NatSet::containsSmall` micro-opt.

**4. Hardest parts / risks / open questions.**
- Preregularity-*modulo-A* (assoc/comm/id/idem collapse checks; manual 11180–11220) and the order-sensitive "break toward earlier declaration" tie-breaking in `findMinSortIndex` must be reproduced exactly to match Maude's least sorts and warnings.
- The precise linear sort ordering is load-bearing (BDD bit layout, `fastTest`, diagram indices) — keep it or an isomorphic invariant.
- BDD backend choice/perf for unification; deciding pure-Rust vs FFI.
- "Late symbols" — `getSortFunction` (`sortBdds.cc:117`) tolerates symbols added after module close; needs growable structures, not fixed arrays.
- `poly` operators: kind-level instantiation lives at the Mixfix/instantiation layer, not Core sort files [INFERRED] — coordinate with A4/A5.
- Multiple range sorts per op (`getRangeSort` returns the first, `sortTable.hh:180`) — edge case to model deliberately.

**5. Proposed Rust module layout** (`src/sort/`): `mod.rs` (Sort, SortId, Kind, leq bitsets, public API); `poset.rs` (topological build + cycle detection, replacing `registerConnectedSorts`/`processSubsorts`); `sort_table.rs` (OpDeclaration, decision-diagram build/`traverse`, least-sort + preregularity); `ctor.rs` (constructor diagram + ctor status); `membership.rs` (SortConstraint, SortConstraintTable, `constrain_to_smaller_sort`); `bdd.rs` (SortBdds: leq/gt relations, per-symbol sort function, `operator_compose` — `#[cfg(feature="unification")]`); `diagnostics.rs` (`sortErrorAnalysis` preregularity/ctor-consistency warnings).
